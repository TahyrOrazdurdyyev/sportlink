# Обновление Sportlink на сервере

Эта инструкция описывает ручной выпуск обновления backend на сервере через Git и Docker Compose. Отправка коммита в GitHub сама по себе **не обновляет сервер**: автоматический workflow деплоя в репозитории не настроен. После `git push` нужно отдельно подключиться к серверу и выполнить команды обновления.

> Перед началом убедитесь, что у вас есть SSH-доступ к серверу и вы знаете путь к клону проекта. Ниже в примерах используются домен `sportlink.com.tm`, IP `216.250.13.53` и ветка `main`; замените их, если фактические параметры сервера отличаются.

## Что входит в этот процесс

Корневой `docker-compose.yml` описывает MongoDB, Redis, backend, Celery worker и Celery beat. Обновление backend может пересоздать три приложения (`backend`, `celery`, `celery-beat`); контейнеры базы данных и Redis при этой команде не пересоздаются.

В текущем Compose-файле нет сервисов сайта и админ-панели. Для них требуется отдельный способ публикации; команды ниже их не обновляют. APK/iOS-приложения также не обновляются на телефонах при деплое backend: мобильные клиенты собираются и распространяются отдельно.

## 1. Подготовить и отправить изменение в GitHub

На рабочем компьютере:

1. Убедитесь, что нужные файлы проверены и тесты для изменения пройдены.
2. Просмотрите изменения и исключите из коммита секреты, `.env`, резервные копии, локальные сборки и посторонние файлы.
3. Добавьте только файлы, входящие в выпуск, создайте коммит и отправьте нужную ветку:

```bash
git status --short
git diff --check
git add путь/к/файлу1 путь/к/файлу2
git diff --cached --stat
git diff --cached
git commit -m "Краткое описание обновления"
git push origin main
```

Перед коммитом проверьте `git diff --cached`: в нём должны быть только ожидаемые файлы. Если используется отдельная ветка, отправьте её вместо `main` и откройте pull request по принятому в команде процессу.

## 2. Подключиться к серверу и проверить рабочую копию

Подключитесь по SSH и перейдите в каталог, где расположен клон репозитория:

```bash
ssh <пользователь>@216.250.13.53
cd <путь-к-клону>/sportlink
```

Проверьте ветку, состояние каталога и текущий коммит:

```bash
git status --short
git branch --show-current
git rev-parse --short HEAD
```

Продолжайте только если это нужный клон и рабочая копия не содержит локальных изменений, которые можно затереть или случайно включить. Не запускайте `git reset --hard`, `git clean -fd` и не перезаписывайте `.env`. Если на сервере есть локальные изменения, сначала выясните, кому они принадлежат и как их сохранить.

Убедитесь, что production `.env` уже настроен на сервере и не хранится в Git. Он должен содержать фактические production-значения, включая `DEBUG=False`, надёжный `SECRET_KEY`, `BASE_URL`, `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS` и параметры MongoDB/Redis. Не выводите секреты командой `cat .env` и не отправляйте их в чат или коммиты.

Проверьте состояние сервисов и конфигурацию Compose:

```bash
docker compose ps
docker compose config -q
```

Если на сервере используется старая команда `docker-compose`, замените `docker compose` на `docker-compose` во всех командах этой инструкции.

## 3. Сохранить резервную копию данных перед обновлением

Сначала зафиксируйте текущую версию кода и создайте резервную копию MongoDB. Команда сохраняет архив в каталоге `backups` на сервере:

```bash
PREVIOUS_COMMIT=$(git rev-parse HEAD)
mkdir -p backups
BACKUP="backups/sportlink-$(date +%Y%m%d-%H%M%S).archive.gz"
docker exec sportlink_mongodb mongodump --db sportlink --archive --gzip > "$BACKUP"
test -s "$BACKUP"
ls -lh "$BACKUP"
printf 'Текущий коммит до обновления: %s\n' "$PREVIOUS_COMMIT"
```

Храните резервные копии в защищённом месте вне Git и проверьте, что файл не пустой. Если MongoDB настроена с аутентификацией или имеет другое имя контейнера/базы, используйте соответствующие production-параметры; не вставляйте пароль непосредственно в историю shell. Не продолжайте обновление, если резервная копия не создалась.

## 4. Получить код и проверить изменения

Обновляйте сервер только fast-forward-ом: так Git не создаст неожиданный merge-коммит на сервере.

```bash
git fetch origin
git pull --ff-only origin main
git rev-parse --short HEAD
```

Убедитесь, что сервер получил ожидаемый коммит. Если `git pull` сообщает о локальных изменениях или невозможности fast-forward, остановитесь и разберите ситуацию; не применяйте принудительный сброс.

Перед пересборкой ещё раз проверьте production-конфигурацию, не печатая значения секретов:

```bash
docker compose config -q
```

## 5. Пересобрать и применить backend

Для изменений backend и общих Python-зависимостей пересоберите и обновите backend вместе с Celery worker и Celery beat:

```bash
docker compose up -d --build backend celery celery-beat
```

Compose оставляет MongoDB и Redis работающими и пересоздаёт только перечисленные приложения и необходимые им зависимости. Не используйте `docker compose down -v`: удаление volumes может уничтожить production-данные.

Если изменение касается только конфигурации уже существующего backend-контейнера и образ менять не нужно, всё равно предпочтительно применять его через `docker compose up -d` для затронутого сервиса, чтобы Compose корректно пересоздал контейнер с новой конфигурацией. Команда `docker compose restart backend` сама по себе не пересобирает образ и не применяет изменённое окружение.

### Изменения MongoDB-схемы или данных

В проекте используются MongoEngine и ручные скрипты миграции; изменение модели не означает, что миграция выполнится автоматически. До деплоя выясните, требуется ли конкретному изменению миграционный скрипт. Запускайте только относящуюся к нему проверенную миграцию и следуйте её инструкции. Не запускайте все скрипты миграции подряд. Убедитесь, что резервная копия создана до изменения данных.

## 6. Проверить результат

Проверьте, что контейнеры запущены, затем изучите последние логи:

```bash
docker compose ps
docker compose logs --tail=100 backend
docker compose logs --tail=100 celery
docker compose logs --tail=100 celery-beat
```

Проверьте API с сервера и затем с внешней сети:

```bash
curl -fsS https://sportlink.com.tm/api/v1/categories/
```

Успешный ответ API и состояние контейнеров `Up` — необходимые, но не единственные проверки. Дополнительно проверьте сценарий, которого касалось изменение (например, вход, создание бронирования или загрузку файла), и убедитесь, что Celery обрабатывает фоновые задачи. Посмотрите логи на ошибки и не публикуйте в них токены или персональные данные.

## 7. Если после обновления возникла проблема

1. Сохраните логи контейнеров и запишите SHA коммита, на котором проявилась ошибка.
2. Если причина очевидна, устраните её в Git, проверьте исправление и выпустите новый коммит обычным способом.
3. Для отката кода создайте revert-коммит для проблемного изменения в рабочем клоне, отправьте его в `main`, затем на сервере выполните `git pull --ff-only origin main` и повторите пересборку затронутых сервисов:

```bash
docker compose up -d --build backend celery celery-beat
```

Не делайте `git reset --hard` и не откатывайте базу автоматически вместе с кодом. Восстановление MongoDB из резервной копии — отдельная операция, которая заменяет данные и может потерять записи, созданные после резервного копирования; выполняйте её только после оценки последствий и согласования.

## Краткий чек-лист выпуска

- [ ] Проверены изменения и тесты на рабочем компьютере.
- [ ] В GitHub отправлены только файлы выпуска; секреты не попали в коммит.
- [ ] На сервере проверены ветка, чистота рабочей копии и production `.env`.
- [ ] Перед изменением данных создана и проверена резервная копия MongoDB.
- [ ] Код получен через `git pull --ff-only`.
- [ ] Пересобраны backend, Celery worker и Celery beat.
- [ ] Проверены статусы контейнеров, логи, API и затронутый пользовательский сценарий.
- [ ] Записан SHA выпущенного коммита и сохранена резервная копия.
